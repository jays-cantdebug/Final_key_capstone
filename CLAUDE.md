# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

"NORMI" — a Web-Based Student Depression, Anxiety and Stress Assessment (DASS-21) for Northern Mindanao Colleges, Inc.: a Laravel 11 school guidance/psychometric records portal (student capstone project). Public registration is disabled; only `psychometrician` and `guidance_counselor` roles are provisioned by seeders. Backend is PHP 8.2/Blade with Laravel Breeze for auth scaffolding (registration removed); frontend uses Tailwind + Alpine.js via Vite (no SPA framework).

The codebase is driven from a large user-owned "Master Prompt" spec, revealed and approved module-by-module. Nearly the full module list is implemented end-to-end: auth/roles, Course/YearLevel/Section management, Student Information Management, Questionnaire Management (+ versions + questions), Classification Thresholds, New Assessment (3-step wizard), AI Classification, Differentiated Flagging, Notifications, Feedback Loop, Assessment History/Results, Counseling Sessions, Reports (PDF), User Management, Settings, Audit Logs.

**Known open gaps**: none tracked as of 2026-07-08. A full design pass (component library, brand palette, differentiated-flag display rules), login page mockup fidelity, a mobile/tablet responsive pass (code-audited and user-visually-confirmed), and an automated test suite covering every domain module are all complete.

**Local DB is MySQL, not SQLite**, despite `database/database.sqlite` existing and `.env.example` defaulting to sqlite: the working `.env` has `DB_CONNECTION=mysql`, `DB_DATABASE=student_mental_health_system`. Check `.env` before assuming which connection is live.

**Seeding requires `ADMIN_DEFAULT_PASSWORD`** to be set in `.env` — `UserSeeder` throws if it's unset; there is no hardcoded fallback password. Change the seeded Psychometrician account's password immediately after first login in any real deployment.

Run PHP commands via `php artisan`, `vendor/bin/...`. Bring up the frontend build with `npm run dev` (Vite) alongside `php artisan serve` for local development.

- Install deps: `composer install` and `npm install`
- Serve app: `php artisan serve`
- Frontend dev server (HMR): `npm run dev`
- Frontend production build: `npm run build`
- Run all tests: `php artisan test` (or `vendor/bin/phpunit`)
- Run a single test file: `php artisan test tests/Feature/Auth/AuthenticationTest.php`
- Run a single test method: `php artisan test --filter=test_method_name`
- Format code (Pint): `vendor/bin/pint`
- Run migrations: `php artisan migrate`
- Fresh DB + seed: `php artisan migrate:fresh --seed` (requires `ADMIN_DEFAULT_PASSWORD` in `.env` first)
- Tinker (REPL): `php artisan tinker`

Test environment uses the `array` driver for cache/session, `sync` queue, and sqlite in-memory `DB_CONNECTION`/`DB_DATABASE` (see `phpunit.xml`) — `RefreshDatabase` tests run fully isolated from the real dev MySQL database (`student_mental_health_system`), never touching or wiping it.

359 tests (`php artisan test`), covering Breeze auth flows plus every domain module: DASS scoring (pure arithmetic), AI classification (`RuleBasedDASSProvider` severity boundaries, provider factory resolution), differentiated flagging (all 0-3 flag-row combinations, notifications going to Guidance Counselors only — never the Psychometrician, tested as an explicit regression), the mandatory Step 3 review (Confirm/Correct consistency rules, flagging off the reviewed severity), the New Assessment wizard end-to-end (name-splitting edge cases, full submit pipeline, duplicate-student blocking at Step 1 and at final save), Student/Questionnaire/Classification Threshold/Counseling Session/Notification/Report/Audit Log CRUD and role gating, cross-cutting authorization (inactive-user login block, rate limiting, the User deactivation safety net), Counselor-facing reviewed levels, the Corrected badge and the role-based Summary Report counts (`CorrectedClassificationVisibilityTest`, the `assessment_summary_*` tests in `ReportsTest`, plus `wasCorrected()`/`effectiveLevel()` unit tests in `tests/Unit/Models/AssessmentTest.php`), and page-load stability (`PageLoadStabilityTest`: x-cloak and server-rendered starting states, font preload URLs matching the built CSS, color-scheme, sidebar scroll restore). Shared fixtures live in `tests/Concerns/InteractsWithDomainData.php` (acting-as helpers, official threshold seeding, a configurable DASS-21 questionnaire version whose per-subscale raw score can be dialed to hit an exact severity band, and `saveAssessmentThroughWizard()` to run the whole wizard with a given Step 3 decision).

## Architecture

### Role-based access model

Authorization is centered on a `role_id` on `User`, not a package like Spatie permissions:

- `Role` (`app/Models/Role.php`) is a simple lookup table (`name`, `display_name`) seeded by `RoleSeeder` with two roles: `psychometrician` and `guidance_counselor`.
- `User::hasRole(string|array $roles)` (`app/Models/User.php`) checks the related role's `name`. `User` has no soft deletes — accounts are deactivated via `is_active`, never deleted/restored.
- Route-level protection uses the `role` middleware alias → `EnsureUserHasRole` (`app/Http/Middleware/EnsureUserHasRole.php`), registered in `bootstrap/app.php`. Usage: `->middleware('role:psychometrician')`.
- Model-level authorization uses Laravel Policies (e.g. `app/Policies/StudentPolicy.php`, `UserPolicy.php`), invoked in controllers via `Gate::authorize(...)`. Simple admin-only pages (Course/YearLevel/Section/Questionnaire/Settings) rely on route middleware alone with no dedicated Policy class.
- `DashboardRouteService` (`app/Services/Auth/DashboardRouteService.php`) maps a user's role to a named dashboard route (`psychometrician.dashboard`, `guidance-counselor.dashboard`, or the generic `dashboard`); `DashboardController::index` redirects there after login.
- Root route `/` (see `routes/web.php`) redirects guests to `login` and authenticated users to `dashboard` — it is not a static view.

When adding a new role-gated feature, follow this same three-layer pattern: route middleware for page access, a Policy + `Gate::authorize` for the underlying model actions (only where per-record nuance exists beyond role), and (if it needs its own landing page) an entry in `DashboardRouteService`.

### Service layer

Controllers delegate persistence/query logic to `App\Services\*` classes rather than querying Eloquent directly. Services are constructor-injected (e.g. `DatabaseManager` for wrapping writes in `->transaction()`). Follow this pattern for new resourceful features: thin controller (auth check + call service + return view/redirect), service holds the actual query/mutation logic.

### AI Prediction Module (`app/AI/`)

Follows the Strategy Pattern, resolved via `config('ai.provider')` (env `AI_PROVIDER`, default `rule_based`):

- `AIProviderInterface::classify(AssessmentPayload): AIClassificationResult` — the only contract callers depend on.
- `RuleBasedDASSProvider` — the default, **functional** provider. Classifies each DASS-21 subscale by querying `classification_thresholds` (no hardcoded cutoffs).
- `ClaudeAIProvider` — also functional. Sends the three subscale scores plus the live `classification_thresholds` (grouped into a snake_case `official_thresholds` JSON object, top tier's max reported as `null` to match DASS-21's open-ended top tier) to the Claude Messages API, forcing a tool-use call (`classify_dass_subscales`, JSON-Schema-enum-constrained) so the reply is structurally guaranteed JSON rather than merely prompted for. Because a threshold lookup is deterministic, the response is always cross-checked against `RuleBasedDASSProvider`'s own result for the same input before being trusted: agreement → the Claude result is used (`ai_provider` recorded as `claude`); any disagreement, malformed response, or request failure → the discrepancy is logged via `Log::warning()` and the rule-based result is returned instead (`ai_provider` recorded as `rule_based`), so an incorrect severity tier is never persisted and `dass_results.ai_provider` always reflects what was actually saved. `classify()` never throws. Configured via `AI_PROVIDER=claude`, `CLAUDE_API_KEY`, `CLAUDE_MODEL` in `.env` — the test suite pins `AI_PROVIDER=rule_based` in `phpunit.xml` regardless of `.env`, so tests never call the live API. Swapping providers must never require touching controllers/services/schema.
- `AIProviderFactory` resolves the active provider; `AIService` is the only class controllers/services call — never instantiate a provider directly.
- `AssessmentPayload` (immutable DTO) carries only `assessmentId` + the three final subscale scores — classification input, not output.

### DASS scoring, differentiated flagging, and the Feedback Loop

- `DassScoringService` is a **pure arithmetic** service: sums raw responses per subscale and doubles them for the final score. It does not classify severity or decide flags — that moved to the AI layer and `FlaggedCaseService` respectively (an earlier draft conflated all three in one service; that's been split apart).
- Scoring (sum × 2) and the official thresholds (top band ending at 42) assume the DASS-21 layout, so `QuestionnaireVersionService::activate()` (including reactivating an Archived version) refuses any version that doesn't have **exactly 7 Depression, 7 Anxiety and 7 Stress questions, all required**, throwing `QuestionnaireVersionLockedException` with a message naming each wrong subscale/count or optional item. The controller returns it under the `activation` error key (not the shared `version` key) so the questionnaire and version pages show it as a toast that stays until dismissed. Drafts can hold any layout; only activation is checked. Only an Active version can be archived, and a questionnaire can't be archived while one of its versions is Active. In tests, build versions with `addDassQuestions()` from `InteractsWithDomainData`, not `DassQuestion::factory()` in bulk (its faker-unique `item_number` runs out past 21).
- The pipeline is split in two. `AssessmentService::reviewAssessment()` runs when Step 3 is first opened: it computes the scores and calls `AIService::classify()`, writes nothing, and its result is cached in session (`assessment_wizard.review`) so the AI is called once per set of responses. `AssessmentService::save()` runs on Confirm & Save / Correct & Save, in one DB transaction: register the student (after the duplicate re-check; skipped for Take Again) → save assessment/responses → save `DassResult` from the cached review (includes `ai_provider`; never re-classified) → `PredictionFeedbackService::submit()` (the review decision) → `FlaggedCaseService::evaluateAndFlag()` on the effective levels. See "New Assessment workflow" below for why student registration happens here rather than at Step 1 of the wizard.
- `FlaggedCaseService::evaluateAndFlag()` evaluates Stress, Depression, and Anxiety **independently**: Stress Severe/Extremely Severe → `flagged_cases` row with `flag_type = counseling_endorsement`; Depression and/or Anxiety Severe/Extremely Severe → separate `flag_type = awareness_notification` row(s), one per triggering subscale. A single assessment can produce 0–3 rows. Notifications go out per newly-created flagged case, to Guidance Counselors only — the Psychometrician is never a notification recipient (she sees the result immediately on submission).
- `DassResult::highestSeverityLevel()` computes an on-the-fly "highest severity" across the three subscales for display purposes (Dashboard/Reports/Counseling Sessions) — this is **not** a stored column; there is no `overall_status`/`overall_flag` in the schema.
- `PredictionFeedback` (Feedback Loop): the Psychometrician's mandatory review decision — Confirm or Correct — made at Step 3 of the wizard *before* anything is saved, and written by `PredictionFeedbackService::submit()` inside `AssessmentService::save()`'s transaction, one row per assessment. There is no post-save Feedback Loop any more: the standalone `PredictionFeedbackController` page and its route were removed in f4c1776, so a review can't be changed after saving (`submit()`'s `updateOrCreate` is never reached a second time). The AI's raw levels stay in `dass_results` (audit trail; still what every Psychometrician screen shows); flagging runs on the effective levels (the correction where one was given). **What the Guidance Counselor sees:** only reviewed levels, via `Assessment::effectiveLevel($subscale)` / `effectiveHighestSeverityLevel()` (same rule as `save()`), plus a "Corrected by Psychometrician" badge (`<x-corrected-badge />`, whole assessment, no level/direction/`data-` attributes) when `Assessment::wasCorrected()` — a Correct with at least one corrected level differing from the AI's (same-level picks and Confirm-with-stored-corrections rows like dev #125 don't count). All three require `result` and `predictionFeedback` eager-loaded and throw `LogicException` otherwise (no silent per-row queries). Counselor-only views (Notifications, Flagged Cases, GC dashboard, counseling session pages/form picker) always use them; shared views (`assessments/show`, `assessments/_table`, `reports/print/assessment`, `reports/print/student-history`) branch on `hasRole('guidance_counselor')` so the Psychometrician's output is unchanged. `FlaggedAssessmentNotification` writes the reviewed level into the message. Scores and the Prediction Feedback card stay visible to both roles. The Assessment Summary Report's severity breakdown is role-dependent: `ReportService::assessmentSummaryData($filters, reviewedLevels:)` counts `effectiveLevel()` for the Guidance Counselor (one extra query for `prediction_feedback`; agrees with the flag totals) and raw `dass_results` levels for the Psychometrician (unchanged); `countsBasis` drives the note in `reports/_summary-counts-basis.blade.php`, shown on screen and in print/PDF. The Audit Log still labels these rows module "Feedback Loop", action "Feedback Loop Submission" (`AuditableObserver`).

### Encryption at rest (RA 10173)

`dass_responses.answer_value`, `dass_results`' six raw/final score columns, and `counseling_sessions.session_notes` use Laravel's `encrypted` Eloquent cast (AES-256) — the columns were widened to `TEXT` to hold ciphertext, and decrypt back to **strings** (not ints), which is safe only because every reader of these columns is a Blade view doing display, never typed PHP arithmetic. Student names, `gender`, and DASS severity *levels* (`depression_level`/`anxiety_level`/`stress_level` — distinct from the encrypted numeric scores) are deliberately **not** encrypted at the column level: name search across the app relies on SQL `LIKE`/`CONCAT` matching, and the Psychometrician Dashboard filters severity levels with SQL `whereIn`, neither of which works against non-deterministic ciphertext. See `SYSTEM_DOCUMENTATION.md`'s "Data Encryption & Privacy" section for the full rationale, including the recommendation to pair this with database-level encryption-at-rest (TDE/encrypted volume) for the fields left in plain text. `php artisan security:encrypt-sensitive-data` (`app/Console/Commands/EncryptSensitiveDataCommand.php`) is the idempotent, one-time backfill for pre-existing plaintext rows — it writes via the query builder, not Eloquent, specifically to avoid flooding Audit Logs via `AuditableObserver`.

### Student domain model

Core entities: `Student` belongs to `Course`, `YearLevel`, and `Section` (all simple lookup tables). `Student` uses `SoftDeletes` — "delete" is really an archive (see `StudentController::destroy` message: "archived successfully"); there is no separate `status` column — soft-delete (`deleted_at`) is the sole active/archived signal. The only sex/gender field is `gender` (Male/Female/Prefer not to say) — there is no legacy `sex` column.

The Students list (`StudentService::paginate()`, shared by the full page and the `X-Live-Search` partial) orders newest registered first: `created_at` desc, then `id` desc as a tie-breaker — never by the string `student_number`. Take Again never writes the `students` row, so a retake doesn't move a student.

`student_number` is **always system-generated** by `StudentNumberGeneratorService` (year-prefixed sequential code) — it is never typed by the Psychometrician on the New Assessment intake form (the only way to register a student — Student Information Management has no create/store routes).

Validation for the Student Information Management update lives in `StudentFormRequest` (`app/Http/Requests/StudentFormRequest.php`), which authorizes at the request level (`authorize()` returns `true`) — actual authorization is done separately in the controller via `StudentPolicy`.

### New Assessment workflow (3-step wizard)

`AssessmentWizardController` drives Student → Questionnaire → Result, with in-progress state held entirely in session (`assessment_wizard.student_data`, `assessment_wizard.responses`) until final submit — **nothing is written to the database until Step 3's Confirm & Save / Correct & Save action**. Step 1 (`AssessmentStudentRequest`) validates the intake form and stages it in session only; scoring and AI classification run when Step 3 opens, in `AssessmentService::reviewAssessment()` (no writes); `AssessmentService::save()` creates the `students` row and the `assessments` row together, in the same transaction, only when the wizard is completed. This means an abandoned wizard (closed after Step 1 or Step 2, a validation error, restarting the flow) leaves no orphan `students` row — earlier drafts created the student row immediately on Step 1, which left dozens of assessment-less student records behind from incomplete runs; that's been fixed by deferring creation to final submit. Duplicate students are refused, not merged: `StudentDuplicateService::findMatches()` compares first name + middle *initial* + last name (trimmed, whitespace collapsed, case-insensitive; only the middle name's first letter; course/year level/section/gender deliberately ignored; final comparison in PHP after a broad SQL pre-filter on `LOWER(REPLACE(name, ' ', ''))`. MySQL and the test suite's SQLite behave identically for ASCII names and for the Ñ middle initial (compared in PHP only), but SQLite's `LOWER()` only lowercases ASCII, so an uppercase non-ASCII letter in a stored first or last name (e.g. `PEÑA`) misses the SQLite pre-filter where MySQL matches it — only MySQL gives the real behaviour for those names). `confirmStudent()` starts every Step 1 POST by clearing the whole `assessment_wizard` session, then: an **active** match always blocks (no override) and sends the Psychometrician to that student's Take Again; an **archived** match only warns, and continuing requires the `confirm_archived_match` box, after which the server-computed archived IDs are staged as `assessment_wizard.acknowledged_archived_ids`. `AssessmentService::save()` repeats the check in its transaction when `$existingStudent` is null and throws `DuplicateStudentException` on an active match (nothing saved; back to Step 1 with a "registered while you were working" panel); archived matches never block at save, and acknowledged ones are written as an "Archived Match Confirmed" audit entry against the new student. The panel (`assessments/create/_duplicate-student.blade.php`) is an inline, dismiss-only (×) panel inside the Step 1 form, not a toast. It is flashed for one page load, so when a submit that had the archived warning on screen (`archived_warning_shown`) fails validation, `showStudentStep()` rebuilds it from old input; `privacy_consent` and `confirm_archived_match` are restored from old input too. The middle initial is `A–Z` or `Ñ` (`/u` regex; `Str::upper` and `StudentDuplicateService::middleInitial()` are multibyte-safe, and Ñ ≠ N). `AssessmentStudentRequest::prepareForValidation()` first NFC-normalizes it with intl's `Normalizer`, so a decomposed Ñ (N + U+0303 combining tilde) is accepted and stored as the single letter. This only happens when the intl extension is enabled (`ext-intl` is in `composer.json`'s `suggest`, not `require`; Herd's PHP has it): `composeToNfc()` checks `class_exists(Normalizer::class)` and otherwise leaves the value unchanged, so without intl a decomposed Ñ is rejected as an invalid format instead of crashing. Take Again is never subject to the check. Known, accepted limitation: a genuinely different person with the exact same first name, middle initial and last name can't be registered through the wizard. The UI takes First Name/Middle Name/Last Name as three separate inputs directly, all three required at the form-validation level in `AssessmentStudentRequest` (`students.middle_name` itself stays nullable at the schema level — this is a stricter data-entry rule, not a DB constraint) — there is no name-splitting heuristic. Because the student isn't persisted until Step 3, `student_number` (system-generated at creation) can't be previewed on the Step 2/3 review screens — those pages only display `full_name`, built from an unsaved `Student` model over the session data (reusing `Student::fullName()`) rather than a real DB fetch. Merging records that are already duplicated is not automated — it would be a manual, Psychometrician-driven action through Student Information Management. Step 3's Confirm & Save / Correct & Save share one form with the three `corrected_*` dropdowns: `PredictionFeedbackFormRequest::after()` refuses Confirm with any correction set and Correct with none set (`corrections` error key), and `submit()` also refuses a Correct whose chosen levels all equal the cached AI review (a same-level pick next to a real change is kept as chosen).

### Routes

`routes/web.php` is the main app route file; `routes/auth.php` (Breeze-generated, registration routes removed) holds auth routes and is required from it. Both roles now have real resource routes, not just a dashboard: Psychometrician owns `students.*`, `questionnaires.*` (+ versions/questions — both nested groups use `scopeBindings()`, so a version under another questionnaire or a question under another version 404s), `users.*`, Settings, Audit Logs, and the New Assessment wizard (its Step 3 save records the review decision — there is no separate feedback route); Guidance Counselor owns `flagged-cases.index`, `notifications.*`, and `counseling-sessions.*`. Counseling Sessions has two tabs: "All Sessions" (the flat `counseling-sessions.index` list) and "By Student" (`counseling-sessions.students.index` / `.students.show`, `StudentCounselingHistoryController` + `StudentCounselingHistoryService`) — one summary row per student plus a per-student history page. These two routes are registered *before* `Route::resource('counseling-sessions', ...)` so `students` isn't captured as a `{counseling_session}` id. `CounselingSessionFormRequest` validates `student_id` only on create (active students only — archived ones can't get new sessions, but their existing sessions and history stay editable/viewable); on update `student_id` is ignored and the `assessment_id` rule is scoped to the session's own student. Follow-up status is derived in SQL, never stored: the latest **Completed** session has `follow_up_required` and no Scheduled/Completed session exists after it → `needed`, or `overdue` once its `follow_up_date` has passed; otherwise `none`. Cancelled/No-Show sessions never count as the "last session" and never satisfy a follow-up. `CounselingSessionFormRequest` enforces that a **Completed** session's `session_date` is not after today (date-level `before_or_equal:today`, create and update; other statuses may be in the future), and that `follow_up_date` is on/after the session date; unticking Follow-up required clears `follow_up_date`, but only when `follow_up_required` is actually sent. Pre-rule dev rows #29 and #31 are still Completed with future dates and were deliberately left as-is — editing them requires correcting the date or status. The per-student PDF reuses the Counseling Report via a `student_id` filter (`ReportFilterRequest`). The Student Information Management profile (`students.show`) stays Psychometrician-only and shows no counseling data — the role split is deliberate. `AssessmentController::show` resolves its back links (Back to Dashboard / Student Profile / Assessment History / Flagged Cases / Notifications / Counseling Session / Counseling History) from the Referer header, never a query parameter: same-host only, the Referer path matched exactly against the target page, the URL rebuilt with `route()` (never the raw Referer) carrying only a per-link whitelist of query keys via `refererQuery()` (Back to Dashboard's per-role list is `DASHBOARD_QUERY_KEYS`, taken from `DashboardFilterRequest` plus the All Assessments paginator's `page`; the Guidance Counselor dashboard has none), and only for a viewer allowed to open the target page; no Referer means no link. Exact path matching makes the links mutually exclusive, so at most one ever applies. Back to Notifications relies on browsers keeping the Notifications list as the Referer across `NotificationController::view()`'s redirect (checked in headless Chrome/Edge). Assessment History/Show and Reports are shared across both roles (some report routes are role-specific, e.g. Flagged Students/Counseling reports are guidance-counselor-only). The Reports hub (`reports.index`) itself only surfaces two cards — Assessment Summary Report (both roles) and a consolidated Flagged Students Report with a `flag_type` filter (guidance-counselor-only); Assessment Report, Student Assessment History, and Counseling Report remain fully functional routes reached from Assessment History, a student's profile, and the Counseling Sessions module respectively, just not duplicated as their own Reports-hub cards. Daily/Monthly Assessment Report and Questionnaire Usage Report were removed entirely (routes, controllers, views).

### Login gating

`LoginRequest::authenticate()` (`app/Http/Requests/Auth/LoginRequest.php`) passes `is_active => true` directly into the `Auth::attempt()` credentials array, so deactivating a user (`is_active = false`) silently blocks login as an "invalid credentials" error rather than a distinct "account disabled" message. Login throttling (5 attempts, RateLimiter, audit-logged lockouts) is implemented per spec.

## Conventions in this codebase

- New PHP files in `app/` generally start with `declare(strict_types=1);` (controllers, services, middleware, migrations added after the initial schema) — match this in new files.
- Constructor property promotion + `private readonly` is used for injected dependencies.
- Views are plain Blade (no view models/Livewire) organized by feature under `resources/views/{feature}/`, with shared partials as `_form.blade.php`-style files and Breeze's `layouts/app.blade.php` / `layouts/guest.blade.php` layouts.
- Every page is a full page load, so markup must look final at first paint: an Alpine `x-show` element that starts hidden needs `x-cloak` (the `[x-cloak]` rule is in `resources/css/app.css`), or a server-rendered `style="display: none;"` when its starting state must still be right without JS (the counseling Follow-Up Date field, the Classification Thresholds Save/Cancel buttons). Layouts preload the Figtree weights they paint with via `layouts/partials/font-preloads.blade.php` (`Vite::asset()` + `crossorigin`); the `<head>` theme script sets both the `dark` class and `color-scheme`. `layouts/app.blade.php` always renders `class="[scrollbar-gutter:stable]"` on `<html>` (not the login, guest or report layouts), so `x-modal`'s scroll lock (`overflow-y-hidden` on `<body>`) and long↔short page changes never change the page width. Fixed overlays can't paint over that reserved strip, so `app.css` colours `<html>`'s background: `page` / `slate-900` normally, and `color-mix(body 60%, …)` — matching the modal's `bg-body/60` backdrop — while `body.overflow-y-hidden` (via `:has()`). If the modal backdrop colour changes, update those rules (a test pins it). See SYSTEM_DOCUMENTATION.md "Page Loading Without a Flash".
- Schema corrections to already-migrated tables are done via **new**, additive migration files (never editing an already-run migration) — see the `2026_07_0*` migrations altering `dass_results`, `flagged_cases`, `system_notifications`, `students`, `users`, and `classification_thresholds` for the pattern, including the MySQL gotcha where a unique index doubling as a FK's supporting index must be dropped/re-added around a column change, not just dropped.
