# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

"NORMI" — a Web-Based Student Depression, Anxiety and Stress Assessment (DASS-21) for Northern Mindanao Colleges, Inc.: a Laravel 11 school guidance/psychometric records portal (student capstone project). Public registration is disabled; only `psychometrician` and `guidance_counselor` roles are provisioned by seeders. **Scope change (2026-10-08):** it is no longer a purely closed staff system. A student can answer the questionnaire on a separate **student device** under `/s`, with no login and no account, and (second approved exception, same day) can also type their own Step 1 details there (see "Student device assessment" below). That is the only student-facing surface and the only unauthenticated area apart from login/password reset and `/up`. Backend is PHP 8.2/Blade with Laravel Breeze for auth scaffolding (registration removed); frontend uses Tailwind + Alpine.js via Vite (no SPA framework).

The codebase is driven from a large user-owned "Master Prompt" spec, revealed and approved module-by-module. Nearly the full module list is implemented end-to-end: auth/roles, Course/YearLevel/Section management, Student Information Management, Questionnaire Management (+ versions + questions), Classification Thresholds, New Assessment (3-step wizard), AI Classification, Differentiated Flagging, Notifications, Feedback Loop, Assessment History/Results, Counseling Sessions, Reports (PDF), User Management, Settings, Audit Logs.

**Known open gaps**: none tracked as of 2026-07-08. A full design pass (component library, brand palette, differentiated-flag display rules), login page mockup fidelity, a mobile/tablet responsive pass (code-audited and user-visually-confirmed), and an automated test suite covering every domain module are all complete.

**Local DB is MySQL, not SQLite**, despite `database/database.sqlite` existing and `.env.example` defaulting to sqlite: the working `.env` has `DB_CONNECTION=mysql`, `DB_DATABASE=student_mental_health_system`. Check `.env` before assuming which connection is live.

**Seeding requires `ADMIN_DEFAULT_PASSWORD`** to be set in `.env` when the default Psychometrician doesn't exist yet — `UserSeeder` throws if it's unset; there is no hardcoded fallback password. `UserSeeder` only creates that account when missing (never resets its password or `is_active`; `UserSeederTest`).

**Security headers:** `StaffSecurityHeaders` is prepended to the `web` group (outermost, so `auth`'s guest redirect gets it too): `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: same-origin`, deliberately no CSP (Alpine needs `unsafe-eval`; inline `<style>`). `/s` keeps only `StudentDeviceHeaders` (`StaffSecurityHeadersTest`). Change the seeded Psychometrician account's password immediately after first login in any real deployment.

## Architecture

### Role-based access model

Authorization is centered on a `role_id` on `User`, not a package like Spatie permissions:

- `Role` (`app/Models/Role.php`) is a simple lookup table (`name`, `display_name`) seeded by `RoleSeeder` with two roles: `psychometrician` and `guidance_counselor`.
- `User::hasRole(string|array $roles)` (`app/Models/User.php`) checks the related role's `name`. `User` has no soft deletes — accounts are deactivated via `is_active`, never deleted/restored.
- Route-level protection uses the `role` middleware alias → `EnsureUserHasRole` (`app/Http/Middleware/EnsureUserHasRole.php`), registered in `bootstrap/app.php`. Usage: `->middleware('role:psychometrician')`.
- Model-level authorization uses Laravel Policies (e.g. `app/Policies/StudentPolicy.php`, `UserPolicy.php`), invoked in controllers via `Gate::authorize(...)`. Simple admin-only pages (Course/YearLevel/Section/Questionnaire/Settings) rely on route middleware alone with no dedicated Policy class.
- `DashboardRouteService` (`app/Services/Auth/DashboardRouteService.php`) maps a user's role to a named dashboard route (`psychometrician.dashboard`, `guidance-counselor.dashboard`, or the generic `dashboard`); `DashboardController::index` redirects there after login.
- Root route `/` (see `routes/web.php`) redirects guests to `login` and authenticated users to `dashboard` — it is not a static view. Every route in `routes/web.php` other than `/` and the Breeze guest pages is behind `auth`. The exception is `routes/student-device.php` (`/s/*`), registered from `bootstrap/app.php` via `withRouting(then:)` under its own `student-device` middleware group (EncryptCookies, AddQueuedCookiesToResponse, `StudentDeviceHeaders`) **instead of** `web`: no session, no CSRF, no auth. `StudentDeviceExposureTest` pins the exact student route list and fails if any other route without `auth` appears (allowlist: `/`, login, forgot/reset password, `/up`; Ignition's `ignition.*` debug routes are excluded and exist only while APP_DEBUG is on).

When adding a new role-gated feature, follow this same three-layer pattern: route middleware for page access, a Policy + `Gate::authorize` for the underlying model actions (only where per-record nuance exists beyond role), and (if it needs its own landing page) an entry in `DashboardRouteService`.

### Service layer

Controllers delegate persistence/query logic to `App\Services\*` classes rather than querying Eloquent directly. Services are constructor-injected (e.g. `DatabaseManager` for wrapping writes in `->transaction()`). Follow this pattern for new resourceful features: thin controller (auth check + call service + return view/redirect), service holds the actual query/mutation logic.

### AI Prediction Module (`app/AI/`)

Follows the Strategy Pattern, resolved via `config('ai.provider')` (env `AI_PROVIDER`, default `rule_based`):

- `AIProviderInterface::classify(AssessmentPayload): AIClassificationResult` — the only contract callers depend on.
- `RuleBasedDASSProvider` — the default, **functional** provider. Classifies each DASS-21 subscale by querying `classification_thresholds` (no hardcoded cutoffs).
- `ClaudeAIProvider` — also functional. Sends the three subscale scores plus the live `classification_thresholds` (grouped into a snake_case `official_thresholds` JSON object, top tier's max reported as `null` to match DASS-21's open-ended top tier) to the Claude Messages API, forcing a tool-use call (`classify_dass_subscales`, each of its three fields enum-constrained in the JSON Schema; the request sets no `strict` mode). What enforces the five allowed tiers is the app's own check, `extractToolInput()`: the reply must contain a `tool_use` block for that tool with all three fields present, each exactly one of the five Title Case tier names, or it is treated as a failure. Because a threshold lookup is deterministic, the response is always cross-checked against `RuleBasedDASSProvider`'s own result for the same input before being trusted: agreement → the Claude result is used (`ai_provider` recorded as `claude`); any disagreement, malformed response, or request failure → the discrepancy is logged via `Log::warning()` and the rule-based result is returned instead (`ai_provider` recorded as `rule_based`), so an incorrect severity tier is never persisted and `dass_results.ai_provider` always reflects what was actually saved. `classify()` never throws because of Claude (HTTP errors, timeouts and malformed replies all fall back), but it does throw the `RuntimeException` that `RuleBasedDASSProvider` raises when no threshold band covers a score, because the rule-based lookup runs first, outside the `try` — and `RuleBasedDASSProvider` throws it in `rule_based` mode too. Step 3 then returns a 500 and nothing is cached or saved. Override Mode refuses any save that would leave such a gap (`ClassificationThresholdFormRequest::after()` → `ClassificationThresholdService::coverageProblems()`: per subscale, the five bands in severity order must start at 0, follow on with no gap or overlap, and the top band must end at `ClassificationThreshold::MAX_FINAL_SCORE` = 42, its stored cap; rows not submitted are checked at their current values), so a gap now needs a direct database edit. `AssessmentPayload::$assessmentId` is never set (classification runs before the assessment row exists), so the `assessment_id` in these log entries is always `null`; match a log entry to an assessment by time and scores. Request timeouts: `CLAUDE_TIMEOUT` (default 12 s total) and `CLAUDE_CONNECT_TIMEOUT` (default 4 s); blank/invalid values use the defaults, and the total is capped at `ClaudeAIProvider::MAX_TIMEOUT_SECONDS` (20) so it always ends, and falls back, before PHP's 30 s `max_execution_time` under `php -S` (on Windows that counts network waits, and hitting it is an uncatchable fatal 500). Configured via `AI_PROVIDER=claude`, `CLAUDE_API_KEY`, `CLAUDE_MODEL` in `.env` — the test suite pins `AI_PROVIDER=rule_based` in `phpunit.xml` regardless of `.env`, so tests never call the live API. Swapping providers must never require touching controllers/services/schema.
- `AIProviderFactory` resolves the active provider; `AIService` is the only class controllers/services call — never instantiate a provider directly.
- `AssessmentPayload` (immutable DTO) carries only `assessmentId` + the three final subscale scores — classification input, not output.

### DASS scoring, differentiated flagging, and the Feedback Loop

- `DassScoringService` is a **pure arithmetic** service: sums raw responses per subscale and doubles them for the final score. It does not classify severity or decide flags — that moved to the AI layer and `FlaggedCaseService` respectively (an earlier draft conflated all three in one service; that's been split apart).
- Scoring (sum × 2) and the official thresholds (top band ending at 42) assume the DASS-21 layout, so `QuestionnaireVersionService::activate()` (including reactivating an Archived version) refuses any version that doesn't have **exactly 7 Depression, 7 Anxiety and 7 Stress questions, all required, numbered 1–21 with no gaps or duplicates, each on its official subscale** (`DassQuestion::OFFICIAL_SUBSCALE_BY_ITEM`, the single source for the mapping; matches `DassQuestionSeeder`, checked by a test), throwing `QuestionnaireVersionLockedException` with one message listing every problem (subscale counts, "Items 6, 8 and 21 are missing.", "Item 25 is not a DASS-21 item…", "Item 4 must be Anxiety, but is Depression.", optional items). Duplicate item numbers are also blocked by the `(questionnaire_version_id, item_number)` unique index, so that branch is defensive. It also refuses a version whose questionnaire's `status` is Inactive/Archived, and `QuestionnaireService::update()` refuses the reverse (setting the questionnaire with the Active version to Inactive/Archived; `status` error key). The version it archives is updated through the model, one by one, so `AuditableObserver` logs it as a normal "Update" (Active → Archived) before the "Questionnaire Activation" entry. In tests, `addDassQuestions()` puts questions on their official item numbers (extras past 7 per subscale get 22+), and `display_order` follows the item number. The controller returns it under the `activation` error key (not the shared `version` key) so the questionnaire and version pages show it as a toast that stays until dismissed. Drafts can hold any layout; only activation is checked. Deleting a question is a **hard** delete (`DassQuestionService::delete()` → `forceDelete()`, Draft only, refused if any `dass_responses` row references it), so its item number/display order are free again; a soft-deleted row used to keep holding the `(questionnaire_version_id, item_number)` / `display_order` unique slots, so a Draft that lost an item could never be activated. Only an Active version can be archived, and a questionnaire can't be archived while one of its versions is Active. In tests, build versions with `addDassQuestions()` from `InteractsWithDomainData`, not `DassQuestion::factory()` in bulk (its faker-unique `item_number` runs out past 21).
- The pipeline is split in two. `AssessmentService::reviewAssessment()` runs when Step 3 is first opened: it computes the scores and calls `AIService::classify()`, writes nothing, and its result is cached in session (`assessment_wizard.review`), so refreshing Step 3, or going back to Step 2 and returning without resubmitting, reuses it. The AI is called once per Step 2 submission, not once per distinct set of answers: every Step 2 POST (`storeResponses()`) clears the cached review, so resubmitting identical answers calls the AI again. The cache is also cleared by Step 1, Take Again, a successful save, a duplicate-student conflict at save, logout and session expiry — but not by a failed Step 3 validation. `AssessmentService::save()` runs on Confirm & Save / Correct & Save, in one DB transaction: register the student (after the duplicate re-check; skipped for Take Again) → save assessment/responses → save `DassResult` from the cached review (includes `ai_provider`; never re-classified) → `PredictionFeedbackService::submit()` (the review decision) → `FlaggedCaseService::evaluateAndFlag()` on the effective levels. See "New Assessment workflow" below for why student registration happens here rather than at Step 1 of the wizard.
- `FlaggedCaseService::evaluateAndFlag()` evaluates Stress, Depression, and Anxiety **independently**: Stress Severe/Extremely Severe → `flagged_cases` row with `flag_type = counseling_endorsement`; Depression and/or Anxiety Severe/Extremely Severe → separate `flag_type = awareness_notification` row(s), one per triggering subscale. A single assessment can produce 0–3 rows. Notifications go out per newly-created flagged case, to Guidance Counselors only — the Psychometrician is never a notification recipient (she sees the result immediately on submission).
- `DassResult::highestSeverityLevel()` computes an on-the-fly "highest severity" across the three subscales for display purposes (Dashboard/Reports/Counseling Sessions) — this is **not** a stored column; there is no `overall_status`/`overall_flag` in the schema.
- `PredictionFeedback` (Feedback Loop): the Psychometrician's mandatory review decision — Confirm or Correct — made at Step 3 of the wizard *before* anything is saved, and written by `PredictionFeedbackService::submit()` inside `AssessmentService::save()`'s transaction, one row per assessment. There is no post-save Feedback Loop any more: the standalone `PredictionFeedbackController` page and its route were removed in f4c1776, so a review can't be changed after saving (`submit()`'s `updateOrCreate` is never reached a second time). The AI's raw levels stay in `dass_results` (audit trail; still what every Psychometrician screen shows); flagging runs on the effective levels (the correction where one was given). **What the Guidance Counselor sees:** only reviewed levels, via `Assessment::effectiveLevel($subscale)` / `effectiveHighestSeverityLevel()` (same rule as `save()`), plus a "Corrected by Psychometrician" badge (`<x-corrected-badge />`, whole assessment, no level/direction/`data-` attributes) when `Assessment::wasCorrected()` — a Correct with at least one corrected level differing from the AI's (same-level picks and Confirm-with-stored-corrections rows like dev #125 don't count). All three require `result` and `predictionFeedback` eager-loaded and throw `LogicException` otherwise (no silent per-row queries). Counselor-only views (Notifications, Flagged Cases, GC dashboard, counseling session pages/form picker) always use them; shared views (`assessments/show`, `assessments/_table`, `reports/print/assessment`, `reports/print/student-history`) branch on `hasRole('guidance_counselor')` so the Psychometrician's output is unchanged. `FlaggedAssessmentNotification` writes the reviewed level into the message. Scores and the Prediction Feedback card stay visible to both roles, as do `assessments/show`'s "Classified by: {ai_provider}" label and its Non-Official Thresholds badge (not role-branched) — neither reveals the AI's level. The Assessment Summary Report's severity breakdown is role-dependent: `ReportService::assessmentSummaryData($filters, reviewedLevels:)` counts `effectiveLevel()` for the Guidance Counselor (one extra query for `prediction_feedback`; agrees with the flag totals) and raw `dass_results` levels for the Psychometrician (unchanged); `countsBasis` drives the note in `reports/_summary-counts-basis.blade.php`, shown on screen and in print/PDF. The Audit Log still labels these rows module "Feedback Loop", action "Feedback Loop Submission" (`AuditableObserver`).

### Encryption at rest (RA 10173)

**Unreadable values (2026-10-09):** `EncryptedInteger` and `EncryptedString` (session notes, replacing the built-in `encrypted` cast, byte-compatible) extend `App\Casts\EncryptedCast`. On `DecryptException` they return `null` (never 0) and flag the model (`TracksUnreadableEncryptedAttributes::isUnreadable()`). `UnreadableEncryptedValues` (scoped) logs one warning per record/column per request. Setting `null` over an unreadable value throws `UnreadableEncryptedValueException`. Views show `<x-unreadable-value />`. The session edit form makes notes optional and the service keeps the ciphertext when they're left empty. `AuditableObserver` detects encrypted casts via the `EncryptedAttribute` interface. `APP_PREVIOUS_KEYS` (in `.env.example`) recovers old data with no code change.

`dass_responses.answer_value`, `dass_results`' six raw/final score columns, `counseling_sessions.session_notes`, and (scope change, 2026-10-08) `remote_assessment_drafts.responses` and `.identity` (both `encrypted:array`; draft codes/tokens/device secrets are stored only as HMAC digests) are encrypted at rest (AES-256-CBC + HMAC, keyed by `APP_KEY`), and the columns were widened to `TEXT` to hold ciphertext. The answer and score columns use the custom `App\Casts\EncryptedInteger` cast (`Crypt::encryptString()` / `decryptString()`, the same primitive as Laravel's built-in cast), which decrypts back to **ints**; only `session_notes` uses Laravel's built-in `encrypted` cast, which decrypts to a string. Student names, `gender`, and DASS severity *levels* (`depression_level`/`anxiety_level`/`stress_level` — distinct from the encrypted numeric scores) are deliberately **not** encrypted at the column level: name search across the app relies on SQL `LIKE`/`CONCAT` matching, and the Psychometrician Dashboard filters severity levels with SQL `whereIn`, neither of which works against non-deterministic ciphertext. See `SYSTEM_DOCUMENTATION.md`'s "Data Encryption & Privacy" section for the full rationale, including the recommendation to pair this with database-level encryption-at-rest (TDE/encrypted volume) for the fields left in plain text. `php artisan security:encrypt-sensitive-data` (`app/Console/Commands/EncryptSensitiveDataCommand.php`) is the idempotent, one-time backfill for pre-existing plaintext rows — it writes via the query builder, not Eloquent, specifically to avoid flooding Audit Logs via `AuditableObserver`. Sessions use the `database` driver, so in-progress wizard data (name, answers, scores, AI levels) sits in `sessions.payload` until saved/cleared/expired; production should set `SESSION_ENCRYPT=true` (`.env.example` ships `false`), which encrypts only the payload — `ActiveSessionGuard` (login-time single-session check, `EnsureSingleActiveSession`, Force Logout) reads only `user_id`/`last_activity`, so it is unaffected. `AuditableObserver` never writes an encrypted attribute (any `encrypted*` cast or `EncryptedInteger`) to `audit_logs`: it stores the marker `[changed]` (`AuditableObserver::ENCRYPTED_MARKER`) on Create/Delete, and on Update only when that field changed (omitted otherwise; non-encrypted originals still come from `getOriginal()`, encrypted ones are read raw so they're never decrypted). Audit rows written before 2026-10-08 were left untouched and can contain session notes as ciphertext or plaintext (Update `old_values` held decrypted notes). Turning it on logs each pre-existing session out on its next request; until then (or expiry) that row still blocks a login elsewhere. `phpunit.xml` does not pin `SESSION_ENCRYPT`, so the suite follows `.env` (it passes either way).

### Student domain model

Core entities: `Student` belongs to `Course`, `YearLevel`, and `Section` (all simple lookup tables). `Student` uses `SoftDeletes` — archiving erases nothing, and the Students page's **Archived** tab (`ArchivedStudentController`, `students.archived.index` / `students.restore`, registered before `Route::resource('students', ...)`, Psychometrician only via `StudentPolicy::restore`) lists archived students and restores them: `StudentService::restore()` refuses while `StudentDuplicateService::findMatches()` finds an active namesake (throws `DuplicateStudentException`; the list disables Restore and shows "Active record exists: <number>"), uses `restoreQuietly()` and writes the single "Restore" audit entry itself (old `archived_at`, new values + `restore_reason`), so the observer doesn't add an "Update"; the student keeps their number and original list position, and nothing is merged. `StudentService::formData($student)` keeps the student's own archived course/year level/section in the edit form, marked "(archived)". The button says **Archive** (as for courses, year levels, sections and questionnaires; `AuditableObserver::ARCHIVED_ON_DELETE` logs their soft deletes as action "Archive", everything else and any `forceDelete()` as "Delete"; entries before 2026-10-08 all say "Delete") — "delete" is really an archive (see `StudentController::destroy` message: "archived successfully"); there is no separate `status` column — soft-delete (`deleted_at`) is the sole active/archived signal. The only sex/gender field is `gender` (Male/Female/Prefer not to say) — there is no legacy `sex` column.

The Students list (`StudentService::paginate()`, shared by the full page and the `X-Live-Search` partial) orders newest registered first: `created_at` desc, then `id` desc as a tie-breaker — never by the string `student_number`. Take Again never writes the `students` row, so a retake doesn't move a student.

`student_number` is **always system-generated** by `StudentNumberGeneratorService` (year-prefixed sequential code) — it is never typed by the Psychometrician on the New Assessment intake form (the only way to register a student — Student Information Management has no create/store routes).

Validation for the Student Information Management update lives in `StudentFormRequest` (`app/Http/Requests/StudentFormRequest.php`), which authorizes at the request level (`authorize()` returns `true`) — actual authorization is done separately in the controller via `StudentPolicy`.

### New Assessment workflow (3-step wizard)

`AssessmentWizardController` drives Student → Questionnaire → Result, with in-progress state held in session — **scope change (2026-10-08):** except that answers given on a student device sit in a `remote_assessment_drafts` row until the Psychometrician submits them (see "Student device assessment" below) — (`assessment_wizard.student_data`, `assessment_wizard.responses`, and `assessment_wizard.questionnaire_version_id` — the version pinned at Step 2: `storeResponses()` stores the version `AssessmentResponseFormRequest` validated against (`questionnaireVersion()`), and Step 3 and `submit()` load that version via `AssessmentService::questionnaireVersion()`, never the currently Active one, so activating another version mid-wizard changes nothing for it. The Step 2 form posts a hidden `questionnaire_version_id`; if it no longer matches the Active version the request fails with the single `QUESTIONNAIRE_CHANGED_MESSAGE` instead of one error per question (a form without the field is validated as before). No pin (an older session) → back to Step 2 with `SUBMIT_QUESTIONNAIRE_FIRST_MESSAGE`. `reviewAssessment()` stamps the review with `questionnaire_version_id`, and `save()` throws `QuestionnaireVersionMismatchException` before writing anything unless every response belongs to the pinned version's questions, every required one is answered, and the review was computed for it; the controller then drops responses/review/pin and returns to Step 2 with its message. Take Again clears the pin like the other keys) until final submit — **nothing is written to the assessment/student tables until Step 3's Confirm & Save / Correct & Save action** (the only earlier write is the temporary, unaudited `remote_assessment_drafts` row of a student-device run — no student record link; it holds the student's own typed details, encrypted, only when they fill in Step 1 on the device — deleted on submit/cancel/every wizard exit/expiry). Step 1 (`AssessmentStudentRequest`) validates the intake form and stages it in session only; scoring and AI classification run when Step 3 opens, in `AssessmentService::reviewAssessment()` (no writes); `AssessmentService::save()` creates the `students` row and the `assessments` row together, in the same transaction, only when the wizard is completed. This means an abandoned wizard (closed after Step 1 or Step 2, a validation error, restarting the flow) leaves no orphan `students` row — earlier drafts created the student row immediately on Step 1, which left dozens of assessment-less student records behind from incomplete runs; that's been fixed by deferring creation to final submit. Duplicate students are refused, not merged: `StudentDuplicateService::findMatches()` compares first name + middle *initial* + last name (trimmed, whitespace collapsed, case-insensitive; only the middle name's first letter; course/year level/section/gender deliberately ignored; final comparison in PHP after a broad SQL pre-filter on `LOWER(REPLACE(name, ' ', ''))`. MySQL and the test suite's SQLite behave identically for ASCII names and for the Ñ middle initial (compared in PHP only), but SQLite's `LOWER()` only lowercases ASCII, so an uppercase non-ASCII letter in a stored first or last name (e.g. `PEÑA`) misses the SQLite pre-filter where MySQL matches it — only MySQL gives the real behaviour for those names). `confirmStudent()` starts every Step 1 POST by clearing the whole `assessment_wizard` session, then: an **active** match always blocks (no override) and sends the Psychometrician to that student's Take Again; an **archived** match only warns, and continuing requires the `confirm_archived_match` box, after which the server-computed archived IDs are staged as `assessment_wizard.acknowledged_archived_ids`. `AssessmentService::save()` repeats the check in its transaction when `$existingStudent` is null and throws `DuplicateStudentException` on an active match (nothing saved; back to Step 1 with a "registered while you were working" panel); archived matches never block at save, and acknowledged ones are written as an "Archived Match Confirmed" audit entry against the new student. The panel (`assessments/create/_duplicate-student.blade.php`) is an inline, dismiss-only (×) panel inside the Step 1 form, not a toast. It is flashed for one page load, so when a submit that had the archived warning on screen (`archived_warning_shown`) fails validation, `showStudentStep()` rebuilds it from old input; `privacy_consent` and `confirm_archived_match` are restored from old input too. The middle initial is `A–Z` or `Ñ` (`/u` regex; `Str::upper` and `StudentDuplicateService::middleInitial()` are multibyte-safe, and Ñ ≠ N). `AssessmentStudentRequest::prepareForValidation()` first NFC-normalizes it with intl's `Normalizer`, so a decomposed Ñ (N + U+0303 combining tilde) is accepted and stored as the single letter. This only happens when the intl extension is enabled (`ext-intl` is in `composer.json`'s `suggest`, not `require`; Herd's PHP has it): `composeToNfc()` checks `class_exists(Normalizer::class)` and otherwise leaves the value unchanged, so without intl a decomposed Ñ is rejected as an invalid format instead of crashing. Take Again is never subject to the check. Known, accepted limitation: a genuinely different person with the exact same first name, middle initial and last name can't be registered through the wizard. The UI takes First Name/Middle Name/Last Name as three separate inputs directly, all three required at the form-validation level in `AssessmentStudentRequest` (`students.middle_name` itself stays nullable at the schema level — this is a stricter data-entry rule, not a DB constraint) — there is no name-splitting heuristic. Because the student isn't persisted until Step 3, `student_number` (system-generated at creation) can't be previewed on the Step 2/3 review screens — those pages only display `full_name`, built from an unsaved `Student` model over the session data (reusing `Student::fullName()`) rather than a real DB fetch. Merging records that are already duplicated is not automated — it would be a manual, Psychometrician-driven action through Student Information Management. Step 3's Confirm & Save / Correct & Save share one form with the three `corrected_*` dropdowns: `PredictionFeedbackFormRequest::after()` refuses Confirm with any correction set and Correct with none set (`corrections` error key), and `submit()` also refuses a Correct whose chosen levels all equal the cached AI review (a same-level pick next to a real change is kept as chosen).

### Login gating

`LoginRequest::authenticate()` (`app/Http/Requests/Auth/LoginRequest.php`) passes `is_active => true` directly into the `Auth::attempt()` credentials array, so deactivating a user (`is_active = false`) silently blocks login as an "invalid credentials" error rather than a distinct "account disabled" message. Login throttling (5 attempts, RateLimiter, audit-logged lockouts) is implemented per spec.

Logout asks first (2026-10-09): the sidebar Logout buttons (`data-logout-trigger`, desktop + mobile drawer) only `$dispatch('open-modal', 'confirm-logout')` (and close the drawer); the one logout form lives in `layouts/partials/logout-modal.blade.php` (included once in `layouts/app.blade.php`, `x-modal ... focusable restore-focus="[data-sidebar-open]"`, Cancel first). `x-modal`'s opt-in `restore-focus` returns focus to the opener on close, or to the given selector if the opener is hidden; modals without it are unchanged.

Deactivation also ends access already open (fixed 2026-10-09; before that a logged-in or "Remember me" user kept access): `UserManagementService::deactivate()` sets `is_active = false` and a new `remember_token` in one save (one "Update" audit entry; `remember_token` is never audited), deletes the user's `sessions` rows when the session driver is `database`, and discards their student-device draft. Every authenticated route group is `['auth', 'active', 'single-session']`: the `active` alias (`EnsureUserIsActive`) logs out an inactive user on their next request with the generic `EnsureUserIsActive::MESSAGE` (never mentions deactivation). Keep `active` before `single-session` on any new authenticated group; `DeactivatedUserAccessTest` checks every authenticated route has it, in that order, and that `/s` doesn't. In feature tests with the `database` session driver, a remember-me cookie only takes over after the user's session rows are gone, and each `actingAs($admin)` request leaves a session row that makes the next one look like a second browser, so that test deletes session rows to simulate expiry.

## Conventions in this codebase

- New PHP files in `app/` generally start with `declare(strict_types=1);` (controllers, services, middleware, migrations added after the initial schema) — match this in new files.
- Constructor property promotion + `private readonly` is used for injected dependencies.
- Views are plain Blade (no view models/Livewire) organized by feature under `resources/views/{feature}/`, with shared partials as `_form.blade.php`-style files and Breeze's `layouts/app.blade.php` / `layouts/guest.blade.php` layouts.
- Every page is a full page load, so markup must look final at first paint: an Alpine `x-show` element that starts hidden needs `x-cloak` (the `[x-cloak]` rule is in `resources/css/app.css`), or a server-rendered `style="display: none;"` when its starting state must still be right without JS (the counseling Follow-Up Date field, the Classification Thresholds Save/Cancel buttons). Layouts preload the Figtree weights they paint with via `layouts/partials/font-preloads.blade.php` (`Vite::asset()` + `crossorigin`); the `<head>` theme script sets both the `dark` class and `color-scheme`. `layouts/app.blade.php` always renders `class="[scrollbar-gutter:stable]"` on `<html>` (not the login, guest, report or student-device layouts; the student-device layout also has no theme script, since its CSP blocks inline script), so `x-modal`'s scroll lock (`overflow-y-hidden` on `<body>`) and long↔short page changes never change the page width. Fixed overlays can't paint over that reserved strip, so `app.css` colours `<html>`'s background: `page` / `slate-900` normally, and `color-mix(body 60%, …)` — matching the modal's `bg-body/60` backdrop — while `body.overflow-y-hidden` (via `:has()`). If the modal backdrop colour changes, update those rules (a test pins it). See SYSTEM_DOCUMENTATION.md "Page Loading Without a Flash".
- Schema corrections to already-migrated tables are done via **new**, additive migration files (never editing an already-run migration) — see the `2026_07_0*` migrations altering `dass_results`, `flagged_cases`, `system_notifications`, `students`, `users`, and `classification_thresholds` for the pattern, including the MySQL gotcha where a unique index doubling as a FK's supporting index must be dropped/re-added around a column change, not just dropped.
